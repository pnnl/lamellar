# lamellar-ucc-sys

This system crate exposes the [UCC](https://github.com/openucx/ucc) C APIs to Rust through `bindgen` so that the Lamellar runtime can utilize a UCC-backed, UCX Lamellae (e.g., for IB fabrics or high-performance networking).

## Overview

- Provides the `lamellar_ucc_sys` `#![no_std]` bindings that the Lamellar runtime and other crates can consume to commiunicate via UCC.
- Builds vendored UCC (1.8.0) from `ucc/` when no `UCC_DIR` is supplied, but it also honors an existing installation when the environment variable is set.
- Links against `ucx`, plus its dependencies, and forwards `rustc` arguments so downstream crates automatically look in the right directories.

### Provenance of `ucc/`

Unlike UCX, libfabric, and MPICH-PMI, **upstream UCC has never published an official "make dist" release tarball** (checked every release from v1.3.0 through v1.9.0-rc1 — none carry a custom dist asset). So `ucc/` is **not** an official release artifact: it's a tarball Lamellar generated itself, by checking out the official `v1.8.0` git tag fresh and running `./autogen.sh && ./configure && make dist` locally (using this project's own Autoconf/Automake/Libtool/Flex toolchain), then vendoring the resulting `ucc-1.8.0.tar.gz` verbatim. The `configure` script it ships was therefore generated by us, not by the UCC maintainers, though from an unmodified checkout of their tagged source — `configure.ac` itself carries no Lamellar changes (UCC's own `configure.ac` already has `AM_MAINTAINER_MODE`, unlike libfabric/MPICH-PMI, so no maintainer-mode patch was needed). `make dist`'s own exclusion rules already keep `docs/` minimal (no bundled images), so nothing was manually stripped beyond that.

**One deviation from the self-generated tarball**: upstream's `src/**/Makefile.am` files at `v1.8.0` omit a number of headers (and one unused `.c` file) from their `_HEADERS`/`EXTRA_DIST` lists — e.g. `src/utils/ucc_class.h`, `src/utils/debug/types.h`, `src/utils/debug/log_def.h`, all of `src/components/tl/ucp/tl_ucp_*.h`, and 27 others — even though other in-tree sources `#include` them directly. Because `make dist` only packages files an `_HEADERS`/`_SOURCES`/`EXTRA_DIST` variable names, that omission carries through to our self-generated tarball too and breaks the build (`fatal error: utils/ucc_class.h: No such file or directory`, etc.) even though the exact same tag's plain `git checkout` has every one of these files. We diffed a fresh `v1.8.0` git checkout against our `make dist` output and copied the ~33 missing `src/` files back in verbatim (unmodified upstream content, just files `make dist` itself drops) to fix it. This is an upstream packaging gap, not a Lamellar source change.
- Currently UCC is built as a shared library. It may be necessary to either set LD_LIBRARY_PATH to include the build directory, typically located at ./target/<release,debug>/build/lamellar-ucc=sys*/out/lib. Alternatively if your crate utilizes a build.rs file you can identify the appropriate library path via the `DEP_UCC_ROOT` and then have cargo set the rpath via something like:
```rust 
if let Ok(lamellar_ucc_lib_dir) = env::var("DEP_UCC_ROOT") {
    let lib_path = PathBuf::from(lamellar_ucc_lib_dir).join("lib");
    println!("cargo:rustc-link-search=native={}", lib_path.display());
    println!("cargo:rustc-link-arg=-Wl,-rpath,{}", lib_path.display()););
}
```

## Building

1. `cargo build` (the build script automatically:
   - copies the vendored `ucc/` tree into `OUT_DIR` and runs Autotools to configure UCC with shared libraries and optimizations enabled — no `autogen.sh`/`autoreconf` step, since the vendored tree already ships a generated `configure`)
   - runs `bindgen` on `wrapper.h` to regenerate the Rust bindings whenever the UCC sources or `UCC_DIR` change.
2. Environment overrides:
   - Set `UCC_DIR` to point at a pre-existing UCC installation.
   - If `UCC_DIR` contains shared libraries, the build script prefers them; otherwise it falls back to the vendored copy.

## Usage

Add `lamellar-ucc-sys` as a dependency when you want Lamellar to target UCX collectives explicitly:

```toml
lamellar-ucc-sys = 0.1.1
```

Downstream crates consume `lamellar_ucc_sys` for low-level collective calls on and rely on the `build.rs` output to know where the headers and libraries live.

## Tested library versions

The bindings are generated from the headers of the UCC being used, and `bindgen` names anonymous C unions and structs by their position
(`ucc_coll_args__bindgen_ty_4`). A UCC release other than those below can renumber them, and the failure is then a compile error in the
crate that uses the bindings (`cannot find struct, variant or union type ucc_coll_args__bindgen_ty_4`), not in this one.

| UCC | Status |
|-----|--------|
| 1.8 (API 1.8) | vendored, the default |
| 1.4.4 | checked, through `UCC_DIR` |
| anything else | untested |

The build script reads `UCC_API_MAJOR`/`UCC_API_MINOR` from the header and prints a `cargo:warning` when the version is outside the range
above. Cargo shows build-script warnings only for path and workspace dependencies, so a crate that depends on the published
`lamellar-ucc-sys` will not see it; check this table before pointing `UCC_DIR` at another release.

## Environment variables

- `UCC_DIR`: optional path to an existing UCC installation; the build script uses it when the required symbols are present.

- `UCC_SHARP_DIR`: optional SHARP install root (`include/sharp/api/sharp_coll.h`, `lib[64]/libsharp_coll`). The vendored UCC is built **without SHARP by default** (`--with-sharp=no`), so a SHARP install that happens to be visible (HPC-X, MOFED) is never picked up. Set this to build `tl_sharp` against that install; `libsharp_coll` is then linked and its directory added to the rpath of the final binary. Two things to know: an HPC-X SHARP also loads HPC-X's own `libucp`/`libuct`/`libucs` (a second UCX next to the vendored one), and it is only useful where a SHARP aggregation manager is reachable. After changing this variable, run `cargo clean -p lamellar-ucc-sys` so the cached UCC build is not reused. Ignored when `UCC_DIR` is set, since a system UCC brings its own SHARP support.

If you unset `UCC_DIR`, the crate automatically builds UCC from source using the vendored copy so that Lamellar can still compile on systems without UCC preinstalled.
